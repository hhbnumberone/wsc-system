# 湿喷台车信息化系统 —— 可运行原型

河南省耿力工程设备有限公司 · 大丘田隧道右线 · 设备 GHP9015H

这是配套《湿喷台车信息化系统产品计划书》的一套**能跑的代码**。计划书里写了 11 项功能
和一个三层架构，这个目录把其中能落到本机上的部分真正实现了一遍：一条命令启动，
浏览器里同时打开车载终端和云平台两端，数据从 CAN 采集到平台上图全程打通。

它的目的不是交付生产系统，而是**证明四件事在代码层面真的成立**：

> 数据不丢不重 · 断网能补传 · 桩号不能造假 · 改了数据能追溯

这四句话在计划书里是承诺，在这里是可以当场演示、可以跑测试、可以在数据库里逐行核对的事实。
实现上有取舍的地方，本文档一律写明白，不藏。

## 一、快速开始

```bat
cd wsc-system
python run_all.py --demo
```

`--demo` = `--reset --seed --open`：清空两端数据 → 生成 30 天平台历史 → 起服务 → 开浏览器。
需要演示"历史曲线有东西可看"时用这个。其余常用组合：

| 命令 | 用途 |
|---|---|
| `python run_all.py` | 保留现有数据直接起（二次演示、接着上次看） |
| `python run_all.py --reset` | 两端数据全部重来，不带历史 |
| `python run_all.py --reset --seed --open` | 等同于 `--demo`，写全是为了可读 |

起来之后：

| 端 | 地址 | 三个页面 |
|---|---|---|
| 云平台 | http://127.0.0.1:8700 | 实时监控 / 历史查询 / 设备台账 |
| 车载终端 | http://127.0.0.1:8701 | 实时监控 / U 盘与修订 / 设置与诊断 |

**Ctrl+C 停止。** 两个子进程会收到 `CTRL_BREAK` 走正常收尾流程（关库、flush CSV、
把手上那批传完），不是被直接杀掉。所以停止可能要等几秒，这是对的，别急着关窗口。

> 端口被占时会直接告诉你是谁占着（PID），不会"看起来起来了"其实少半屏数据。

## 三、架构说明

### 3.1 三层与数据流向

```
   ┌──────────── 车载终端 (terminal/) ────────────┐
   │                                              │
   │  can_bus/simulator.py                        │
   │    │ 每 2 秒一帧，16 个参数                   │
   │    ▼                                         │
   │  app.py  组装 Frame（定死 record_id/ts）      │
   │    │           │                             │
   │    │           └──► store.py ──► frames/*.csv  ← 不可变原始日志
   │    ▼                    │
   │  store.py ──► outbox（发件箱，pending）       │
   │                    │                         │
   │                    ▼                         │
   │            uploader.py  组批 → 发送 → 回收执  │
   │                    │                         │
   │            network.py  链路状态机             │
   │                    │                         │
   │            client.py   唯一的 HTTP 出口       │
   └────────────────────┼─────────────────────────┘
                        │  POST /api/upload
                        │  POST /api/ack
                        ▼
   ┌──────────── 云平台 (server/) ────────────────┐
   │  main.py → api.py                            │
   │    ├─ 幂等入库：record_id / batch_id 双主键   │
   │    ├─ 桩号校验：pile_id ∉ piles → 整批 REJECTED│
   │    ├─ alarms.py 边沿 + 回滞判定 → alarms 表   │
   │    ├─ frame_revisions 只追加，不覆盖 frames   │
   │    └─ web/ 三个页面                           │
   └──────────────────────────────────────────────┘
```

两条**互不依赖**的落盘路径是这套设计的地基：采集一路写 CSV，上传一路走 outbox。
断网只影响后者，所以断网时曲线照样在走（终端首页那句提示说的就是这件事）。

### 3.2 不丢不重怎么成立

**不重**靠两个主键加一个内容寻址的批次号：

- `frames.record_id PRIMARY KEY` —— 同一帧重复入库直接被约束挡掉；
- `batches.batch_id PRIMARY KEY`；
- `batch_id = "{device_code}.{sha1(sorted(record_ids))[:16]}"`，**由内容算出**，不是随机数
  也不是时间戳。所以重传同一批，服务端算出来是同一个 `batch_id`，认出这是重放，
  **返回原回执**（盖上 `duplicate_batch: true` 的戳）而不是新开一张。

除了 `batch_id`，协议里还有第二层 `content_digest` —— 整批**数值内容**的摘要。
这一层是必须的：有人截获一个批次、改掉数值再原样重放，`batch_id` 是不变的
（它只由 record_id 集合决定），只有内容摘要能抓住。两层对不上就整批拒收并留痕。

这一条是整个"不重"的地基：因为批次号可从内容重算，客户端不需要记住"我发过哪批"，
崩溃重启后重新组出同样的批次，服务端自然认出来。

**不丢**靠五个环节，任何一个单独看都不够：

1. **CSV 先落盘** —— 数据到手先写原始日志，后面所有环节都失败也不影响这条；
2. **outbox 是唯一发件箱** —— 行必须先进 outbox 才可能被上传；
3. **回执才改状态** —— HTTP 200 但 body 解析不出合法回执 = 网络错误，退回 `PENDING`，
   绝不因为"看起来成功了"就标 `UPLOADED`；
4. **`INFLIGHT` 中间态 + 启动 reconcile** —— 这是崩溃恢复的关键。没有这个态，
   进程在"已发出、未收到回执"的瞬间崩掉，那些行会永远卡在非终态、
   既不会被重试也不会被算作待传，成为永久的数据黑洞。有了它，
   重启时 `reconcile()` 扫出超时的 `INFLIGHT` 行放回 `PENDING`；
5. **清理永不删 pending** —— 30 天清理只删普通表态的行。

> 重新启动时日志里会出现 `启动恢复：补齐 N 条、回收 M 条、K 个批次标为丢失`。
> `K` 是**账本**条目：进程被杀时正处在 `SENDING` 的批次行，没有任何数据挂在上面
> （数据行早已由 `release_batch` 放回 `PENDING`，之后重新组批传走了），
> 所以它和 `M=0` 同时出现是正常的，不是数据丢失。这一条专门写在这里，
> 是因为演示现场被人问到时"回收 0 条"配"K 个批次丢失"看着像矛盾。
>
> 想在客户面前验证这句话：起终端前先看 `local_batches` 里那几个 `lost` 行，
> 再 `SELECT status, COUNT(*) FROM outbox GROUP BY status` —— 只会看到 `uploaded`，
> 没有 `pending`、没有卡在中间的。数据一条没少。

### 3.3 桩号为什么造不了假

计划书里"桩号不可录入"和"U 盘可修改"表面上打架，实际上是一件事的两面：
**原始值永久保留，修改是新增一条可追责的修订。**

桩号有三层防线，任一层单独都拦得住：

1. **终端 UI 上没有桩号输入框** —— 不是禁用了，是不存在。桩号只能从按里程排序的
   可点清单里选。测试 `test_index_page_has_no_input_at_all` 直接断言首页没有任何
   `<input>`，`ALLOWED_INPUTS` 白名单只放行 U 盘页的操作人和备注两个框；
2. **终端导入 CSV 时校验** —— `pile_id` 必须在本地的平台清单缓存里，
   不在就标冲突、整包拒绝导入；
3. **服务端入库再校验** —— `pile_id ∉ piles` 则整条 `REJECTED: PILE_NOT_ISSUED`。

所以 U 盘能改的是**测量值**。桩号即便要改，也只能"从平台清单里重选一个"，
永远无法自由写一个里程进去。这句话在客户面前可以直说。

### 3.4 工点与设备编号：能录入，但不能自己编

计划书里的"现场录入工点 ID 与设备编号"，落在终端「设置与诊断」页最上面那张卡片上：
两个输入框 + 两个按钮（「1. 请平台核对」「2. 保存并生效」）。改身份不用开记事本，
但**判定权在平台**，这一步不能省。

**这里有两个输入框，桩号那边一个都没有 —— 两者不矛盾**，因为它们防的不是同一件事：

| | 桩号 | 工点 ID / 设备编号 |
|---|---|---|
| 能录入吗 | 不能，只能点选 | 能，手打 |
| 谁说了算 | 平台下发的桩号清单 | 平台的工点档案 + 核对接口 |
| 平台不认时 | `pile_id ∉ piles`，逐条拒收 | 工点不在档案 → 409 当场拒；设备编号允许首次自报 |

桩号那三层防线守的是"数值不能造假"，身份录入守的是"归属不能乱挂"。所以前者不给输入框，
后者给 —— 现场换工点、换车是真会发生的事，堵死反而逼人去改配置文件。
但两者最后都回到同一句话：**平台不认的，进不了库。**

设备编号允许改，但要**核对 + 留痕**：平台此前没有这个编号，就按自报信息建档，
并在「设备清单」的说明列写明"终端自报，未核实"；改完在平台「审计」页留下一条
`identity_change`（原工点/编号/桩号 → 新工点/编号/桩号）。老档案不删 —— 它名下那些
历史数据还得靠旧编号查。核对接口本身**不写库**：核对是给人看的一步，用户可能核对了又反悔，
归属的实际变更走心跳，好处是持续对齐（一次性通知只要那次请求失败，平台上的归属就永远停在旧工点）。

**换编号前必须先结清欠账。** `record_id`、`batch_id`、`event_id` 里都嵌着 `device_code`，
服务端又逐条校验 `parse_record_id(rid)["device_code"] != batch.device_code`，对不上就整批拒收；
而上行只有 `/api/upload` 一条路。所以 outbox、修订队列、审计队列里只要还有非终态的行，
换身份就会被拦下并提示"还有 N 条欠账没传完"。对客户的说法很直白：
**设备换了编号，等于换了身份，欠账得先结清。**

> **两个演示工点的里程区间不许重叠。** `piles.pile_id` 是全局主键，`DQTYX-ZK` 配的是
> 104 907~105 707、`SML-ZK` 是 106 000~106 800，中间特意留着空档。配成重叠的话，
> `ensure_piles()` 的 `INSERT OR IGNORE` 会把后一个工点重叠部分的桩号**静默丢掉** ——
> 不报错，只是桩号少一截，等发现时已经没法回溯。加新工点前先确认里程段。

### 3.5 修订：只追加，不覆盖

`usb_sync.py` 里 `FROZEN_FIELDS = (record_id, device_code, ts_device, ts_epoch, seq, pile_id)`
—— 这六个字段任何情况下不许改。允许改的只有测量值，且必须带：

- `reason_code`（四选一：数值失真 / 传感器故障 / 桩号修正 / 其他）
- `reason_note`
- `operator_name`（空的一律拒绝：**修订是要追到人的**）

改动写进 `frame_revisions` 表，`frames` 原值一个字节都不动；
平台显示"有效值 = 原始值 + 最新修订"。每次导出 / 导入 / 手动上传都作为
audit 事件单独上传，**即使数据本体还没传上去**。

对客户的说法是："不是不允许改，而是谁改的、什么时候、为什么、改成什么，
平台全留痕，原值永久保存。"

### 3.6 报警：边沿触发 + 回滞

2 秒采样下用裸阈值判定，参数在阈值附近抖动会**每秒刷一条报警**，
平台列表十秒钟就爆炸——演示现场第一个穿帮的就是这里。

`server/alarms.py` 的做法：

- 持续越限 `min_duration_s = 3` 秒才触发（边沿，不是电平）；
- 恢复后要稳定 `clear_after_s = 10` 秒才清除；
- 阈值带 5% 回滞带，防止在阈值线上来回翻；
- 同一个 `(device, param)` 同时只有一条 active。

注入一次泵送压力越限，平台**只多一条**报警 —— 这一条就是给客户看的。

### 3.7 补传排序

`backlog > 0` 时终端只走按 `ts_epoch` 排序的 FIFO，清空之后才恢复实时。
不这么做的话，补传的旧数据和实时的新数据混在一起上传，
平台曲线会出现时间倒挂：先出现了 15:40 的点，然后 15:39 的点又插进来。

### 3.8 喷浆循环

计划书截图里有"喷浆记录：开始-结束-方量"，所以采集侧必须有循环检测的生产者，
否则 `cycles` 表永远空着。判定条件：

- **开始**：电机启动 且 泵送压力 > 3 MPa，持续 3 秒
- **结束**：泵送压力 < 1 MPa，持续 10 秒
- **方量**：取 `pump_volume`（累计泵送方量计数器）的差值

`pump_volume` 是**第 16 个参数**，在注册表里明确标注为"截图 15 参数之外的补充项"——
不加它就没有方量的来源。这一点在产品文档和代码里都写明，不含糊过去。

### 3.9 参数注册表是唯一事实来源

16 个参数的 key / 中文名 / 单位 / 正常域 / 报警域只在 `common/params.py` 写一遍。
模拟器、终端界面、服务端判定、CSV 表头、平台前端**全部从这里取**。

不是洁癖：这五处但凡各写一份，改一个阈值就要改五个地方，
漏掉一处的结果是"终端显示正常、平台判成报警"——这种 bug 查起来极费时间。

## 四、演示剧本

下面这套顺序是按"从通链路到证承诺"排的，大约 12 分钟。
每段都写清楚**操作**、**看到什么**、**这证明了什么**，
被客户打断问"这是真的吗"的时候，可以直接把数据库打开给他看。

### 场景 0 · 起环境（1 分钟）

```bat
python run_all.py --demo
```

浏览器会自动开两个标签页。把两个窗口并排摆好，左边平台，右边终端。

### 场景 1 · 链路是通的（1 分钟）

**操作**：终端首页看着不动，平台首页也看着。

**看到什么**：
- 终端：大臂角度、泵送压力等曲线在实时滚动，右下角"上传记录"里批次一条条 `ACKED`；
- 平台：设备列表里 GHP9015H 是**在线**，参数值跟着跳，最近帧时间就是当前。

**证明了**：CAN → 终端 → 网络 → 平台这条全链路是活的，不是各自演示的假数据。

### 场景 2 · 断网缓存 + 补传（3 分钟）

**操作**：
1. 终端首页点红按钮 **「模拟断网」**；
2. 等 20–30 秒（可以让页面自己跑，正好用来讲话）；
3. 再点一次 **「恢复联网」**，然后盯着补传进度走完。

**看到什么**：
- 点下去之后：终端状态栏转 `离线`，采样曲线**照常在走**（关键！），
  "待传"计数开始往上涨，平台那边设备转**离线**、曲线停住不动了；
- 恢复之后：终端计数掉回 0，平台曲线**刚才那段空洞被填上**，时间戳是连续的。

**证明了**：不丢。断网期间一条都没丢，全在本地发件箱里排着队。

**可以顺手打开给他看**：`data/terminal/local.db` 的 `outbox` 表，
断网那段时间的行状态是 `pending`——数据一直在硬盘上，不是内存里。

### 场景 3 · 不重（1.5 分钟）

仓库里带了脚本，不用手搓 JSON。开一个新窗口：

```bat
python tools\prove_idempotent.py
```

它用**和终端上传器完全同一套** `Batch` / `make_batch_id` 组一个合法批次，
然后打三个回合：

```
① 首次上传
  [OK]  HTTP 200  accepted=3  duplicate=0  rejected=0  status=acked
  [OK]  平台帧总数  1055 -> 1058（+3）

② 原样再传一次（模拟网络重试 / 崩溃后重启重传）
  [OK]  回执带 duplicate_batch 戳：duplicate_batch=True
  [OK]  平台帧总数  1058 -> 1058（没变 —— 幂等成立）
  [OK]  回执内容与首次逐字一致（原回执重放，不是新开一张）

③ 改掉一个数值再传（模拟截获批次后偷偷改数）
  [OK]  HTTP 200 —— 该 batch_id 已存在，但本次上传的内容与已入库的不一致，整批拒绝
  [OK]  平台帧总数  1058 -> 1058（原值没被覆盖）
```

**看到什么**：第 ② 回合平台返回的**是当初那张原回执**，一字不改，
只在上面盖一个 `duplicate_batch` 戳 —— 计数看起来还是 `accepted=3`，
但帧总数一动不动。这也是有意的：终端崩溃重启后重传，拿到的回执要和第一次完全一致，
它才能据以推进自己那批的状态机。

**证明了**：不重。批次号是从内容算出来的，重放会被认出来，而不是插进去两份。

**第 ③ 回合是重点，值得多讲一句**：光靠 `batch_id` 判重是不够的 ——
有人截获一个批次、改掉数值再原样重放，`batch_id` 是不变的。
所以协议里还有第二层：`content_digest`（整批**数值内容**的摘要）。
两个对不上就整批拒收并留痕，原值永远不被覆盖。

> 脚本里那个"近 24 小时帧总数"取的是 `/api/overview`，也就是**平台首页仪表盘上
> 显示给客户看的同一个数字**，不是脚本自己去数据库数的。被问"你这脚本是不是自己数的"
> 的时候，指着平台页面回答。

### 场景 4 · 桩号造不了假（1.5 分钟）

**操作**：
1. 在终端页面上找桩号输入框——**找不到**。桩号只能从清单里点。
   （「设置与诊断」页顶上确实有两个输入框，那是**工点 ID 和设备编号**，
   见场景 8 和 [3.4](#34-工点与设备编号能录入但不能自己编)。桩号仍然没有输入框。）
2. 打开一个导出的 CSV，手工把某一行的 `pile_id` 改成一个不存在的里程
   （比如 `ZK999+999`），存盘，然后走"校验比对"。

**看到什么**：导入被拒，报告里明确写出 `PILE_NOT_ISSUED`，整包不导入。
即使绕过界面直接 POST 到平台，服务端也会拒，并给出 `REJECTED: PILE_NOT_ISSUED`。

**证明了**：桩号不可伪造。三层防线，绕得过一层绕不过第二层。

### 场景 5 · 改了数据能追溯（3 分钟）

这是整套演示的重头戏，也是客户最会问的一段。

**操作**：
1. 终端 **U 盘与修订** 页 → ① 选范围 → **导出到 U 盘**；
2. 用记事本打开包里的 CSV，把两行的 `pump_pressure` 改成明显不同的值，存盘；
3. 回到页面 → ② 选那个包 → **校验与比对** → 报告里列出 2 处差异；
4. ③ 填操作人（比如"张工"）、选原因（数值失真）、写备注 → **导入为修订**；
5. ④ 修订队列里出现那两条；
6. 切到**平台 → 历史查询**，定位到那两行。

**看到什么**：那两行有 **「修正」** 标记；点开能看到**原值 / 新值 / 经手人 / 原因 / 时间**，
原值还在，没有被覆盖掉。

**证明了**：可追溯。改是可以改的，但改不了隐身的。

**一定补一句**："系统不是不允许改数据，工程上确实会碰到传感器漂移、接线反了这种情况。
我们要保证的是改完以后，原值还在、谁改的能追到人。"

### 场景 6 · 报警不刷屏（1.5 分钟）

**操作**：终端 **设置与诊断** 页 → 故障注入 → 点 **「泵送压力升高」**，
等十来秒，再看平台。

**看到什么**：
- 平台该参数行变红，报警列表**只多出一条**（不是十几条）；
- 故障注入面板上能看到这条故障还剩多少秒自动解除；
- 解除之后过 10 秒，报警自动清除，状态恢复。

**证明了**：报警是经过工程处理的，不是拿阈值硬套。这一条对懂行的客户特别有说服力——
他们自己厂里的系统多半是刷屏的。

### 场景 7 · 崩溃也不丢（1.5 分钟，可选但很值）

这一段**不能**在 `run_all.py` 起的环境里做 —— 一端挂了它会主动把另一端也停掉
（这是有意的：只起一半的演示环境比完全起不来更难查，页面上有数据但另一端的操作全无效，
现场会先怀疑是代码 bug）。

所以这一段换成两个窗口分开起：

```bat
:: 窗口 A
python -m server.main

:: 窗口 B
python -m terminal.app
```

**操作**：等终端传上一批数据之后，**不要按 Ctrl+C**，直接在任务管理器里
结束窗口 B 的 python 进程（模拟死机 / 断电 / 保险丝烧了），然后重新起终端：

```bat
python -m terminal.app
```

**看到什么**：
- 启动日志出现 `启动恢复：补齐 N 条、回收 M 条…`；
- 之前没传完的数据自动续传，平台那边**没有重复、没有缺行**；
- 平台曲线在重启前后是连续的，中间没有断口。

**证明了**：连崩溃都考虑过了。`INFLIGHT` 中间态就是为这一刻设计的 ——
没有它，死在"已发出、未收到回执"那一瞬间的数据会永远卡住，
既不被重试也不被算作待传。

**做完记得关掉两个窗口**，回到 `python run_all.py` 的用法。

### 场景 8 · 现场录入工点和设备编号（2 分钟）

**操作**：
1. 终端 **设置与诊断** 页最上面那张卡片「工点与设备（现场录入）」，两个输入框；
2. 先故意填一个平台上没有的工点（`DQTYX-XX`）→「1. 请平台核对」——
   当场被拒，并把平台上现有的工点列出来；这就是"工点不能自己编"；
3. 改成 `SML-ZK`（演示用的另一个工点，里程 106 000~106 800），
   设备编号填 `GHP9015H-02` →「1. 请平台核对」——通过，
   并提示这台车此前登记在「大丘田隧道右线」，属于**转场**；
4. 「2. 保存并生效」——回「实时监控」页看顶栏工点变了、作业桩号整列换成了 ZK106 段。

**看到什么**：屏幕上那两条 `identity_change` 的留痕随后出现在平台「审计」页；
平台「设备清单」里多了一条新编号，说明列写着"终端自报，未核实"；
旧设备档案还在（它名下的历史数据还得靠旧编号查）。

**证明了**：计划书说的"现场录入"是真的在车载屏上做的，不用开记事本；
但录入不等于随便录 —— 判定权在平台。

**反例（很值得演）**：先点「模拟断网」攒几条没传上去的数据，再回来点
「2. 保存并生效」→ 被闸门拦住，提示还有 N 条欠账。理由见
[3.4](#34-工点与设备编号能录入但不能自己编)：每条数据的 ID 里都嵌着设备编号，
换了身份再传，平台按设备不匹配会整批拒收。

**演完记得改回来**：再把工点填回 `DQTYX-ZK`、设备编号填回 `GHP9015H`，
核对 + 生效即可 —— 这一步本身也是一次正常的转场。

- [ ] 确认桩号清单加载出来了（终端首页上方显示当前桩号，比如 `ZK105+707`）

- [ ] 场景 8（现场录入）要用**另一个工点**，确认 `config\config.json` 的 `sites` 里
      有 `SML-ZK`；想让"平台第一次见到这台车"那句提示也演出来，
      就挑一个还没在平台「设备清单」里出现过的设备编号

**讲之前想清楚**

- [ ] 场景 2（断网）和场景 5（修订）要留足时间，别的可以快；
- [ ] 场景 5 改的那两行，改成一个**肉眼就能看出差别**的值（比如 4.2 → 9.9），
      别改成 4.2 → 4.3 那种，观众看不出来就白改了；
- [ ] 准备好回答"这跟 XX 厂的系统有什么不一样" —— 答案是场景 3 和场景 5：
      幂等回执 + 只追加修订，这两条大部分同类产品没有。

**万一卡住**

| 现象 | 处理 |
|---|---|
| 平台页面打不开 | 看黑窗口里平台那行日志，多半是端口被占 |
| 终端曲线上有值但平台不动 | 看终端状态栏是不是"离线"；是就点"恢复联网" |

**千万别做的事**

- 不要用 `Ctrl+C` 之外的方式关黑窗口（直接点 × 会留残留进程占端口）；
  真留了就用检查表第一项的办法放掉；

## 六、配置说明：演示值与生产值的差异

`config/config.json` 里有几处**为了演示而调过**的值，这里明写，不藏着：

| 配置项 | 演示值 | 生产建议 | 为什么演示要改 |
|---|---|---|---|
| `upload.interval_s` | 2 | 60 | 计划书 4.2 写的是"按 1 分钟粒度上传"。演示时 60 秒一批，观众会以为系统卡住了；改成 2 秒才能看到数据在流 |
| `acquisition.sample_interval_s` | 2 | 1~5 | 模拟器每 2 秒一帧，够让曲线动起来又不至于把日志刷爆 |
| `retention.frames_days` | 400 | 按客户要求 | 平台留 400 天；终端 CSV 留 30 天（`retention.csv_days`） |

**平台保留天数和终端 CSV 保留天数是两个独立配置**，互不干涉。
这一点必须说清楚，否则演示时会有人以为"平台删了终端也没了"。

真实 CAN 接入：把 `can.source` 从 `"sim"` 改成 **`"real"`**，
配好 `bustype` / `channel` / `bitrate` / `signals`（按设备 DBC 填信号表）。
Windows 上**没有 SocketCAN 子系统**，真车要走 PCAN / Kvaser / ZLG 这类厂商驱动
（`bustype` 填 `pcan` / `kvaser` / `zlgcan`）。

换数据源的判断只有 `can_bus/build()` 一处，上层采集与上传逻辑一行都不用改。

`python-can` 是惰性导入。**真车适配器建不起来时终端不会退出** ——
采集循环把它记成"数据源不可用"并继续重试，界面上明确显示"没数据"。
现场最常见的情况就是 CAN 卡还没插好，这时候要的是一块看得懂的提示，
而不是进程直接挂掉让整个终端黑屏。

★ = 会报警的参数。前 15 个对应计划书截图；`pump_volume` 是为"喷浆记录：方量"

这条是拿真实工况对过的，不是想当然。

## 八、测试

```bat
python -m unittest discover -s tests -v
```

当前 **347 个用例全绿**。测试重点不是覆盖率，而是把四句承诺钉死在无界面的层面：

| 文件 | 钉住的事 |
|---|---|
| `test_common.py` | 参数注册表一致性、时间工具、ID 格式、CSV 往返 |
| `test_upload.py` | **同一批次 POST 两次 → 行数不变、回执相同** |
| `test_store.py` | CSV 轮转、30 天清理不删 pending、reconcile 回收 |
| `test_uploader.py` | 断网缓存 / 超时重试 / `INFLIGHT` 回收 / 补传排序 / 部分拒收 |
| `test_identity.py` | 工点/设备核对与生效：闸门、4 份 `device` 副本同步、桩号整列换、留痕 |
| `test_usb_sync.py` | 导出 → 改 → 导入 → 修订生成；冻结字段拒改；截断文件拒收 |
| `test_terminal_web.py` | **起真的 HTTP 服务**打每一个路由；前端 DOM id 契约 |
| `test_platform_web.py` | 平台三页路由与静态资源；**状态码真的发得出去**（见下） |
| `test_tools.py` | 演示脚本造的数据平台收不收、`row_hash` 覆盖没覆盖满 |

有四个测试值得单说，都是踩过坑之后加的：

- `test_every_api_path_in_js_is_served`（`test_terminal_web.py`）——
  从 `app.js` 里正则扫出所有 `/api/...` 然后逐个请求。
  这条是冲着"前端调了一个服务端根本没实现的接口"去的；
- `test_shared_helpers_do_not_hard_require_page_specific_ids`（同上）——
  三个页面共用一个 `app.js`，共用函数如果硬取某个页面才有的 id，另外两页就会崩；
- `test_row_hash_covers_exactly_the_schema_columns`（`test_tools.py`）——
  **这条当场抓到过一个真 bug**：演示脚本原先照记录字典另拼了一个 flat 去算哈希，
  少了 `quality` 和 `source` 两列，于是同一批数据脚本算出的 `row_hash`
  和终端算出的不一样。而且它不重走脚本的拼法（那样两边一起错还是能对上），
  是从协议里收到的记录**倒推**：schema 里的每一列都必须能从记录里取到；
- `HttpStatusTests`（`test_platform_web.py`）—— **也抓到过一个真 bug**。
  这个文件里其它用例都是直接调 `dispatch()`，看的是它的**返回值**；
  而线上真正发出去的那个状态码，是 `main.py` 另外决定的。当时
  `main.py` 里有一句 `status, payload = self._jsonable(payload)`，
  而那个函数写的是 `return 200, payload` —— 于是业务侧的 400 / 404 / 409
  到了线上全变成 200，而所有调 `dispatch()` 的用例照样全绿。
  所以这一类**起真的 `ThreadingHTTPServer`，看响应行**。
  后果不是理论上的：终端靠 4xx 分辨"平台明确拒收"（不该再重试）和
  "没连上"（该退避重传），平台永远回 200 的话，一次整批拒收要重传 8 次、
  耗时几分钟才落成 REJECTED，原因码还在重传路上丢了。

**顺序原则**：先用无界面的单测把"不丢不重"钉死，再上界面。
状态机的正确性不依赖 UI，而 UI 依赖状态机。所以这些测试比页面更能说明系统是对的。

## 九、已知限制 / 明确不做

原型就是原型，下面这些**没做**，演示时被问到照实说：

- **真实 SocketCAN** —— Windows 没有这个子系统。真车适配器已写好
  （`can_bus/python_can_source.py`），但需要厂商驱动才能跑起来；
- **视频监控、轨迹回放、BIM、报表** —— 计划书里的后续迭代项，本次不做；
- **外部接口管理、登录 / 权限 / 多租户** —— 演示环境不需要，也不影响四个承诺的成立；
- **WebSocket** —— 1 秒轮询足够，加了只是多一个需要维护的连接状态；
- **每设备独立阈值管理** —— 当前阈值是全局的，覆盖写在 `config/thresholds.json`；
- **平台侧的工点 / 设备台账管理界面** —— 工点档案来自 `config/config.json` 的
  `sites` 段（改完重启平台即生效），设备档案由终端自报或心跳自动建立。
  「现场录入」本身已经在终端界面上做完了（见
  [3.4](#34-工点与设备编号能录入但不能自己编)），缺的是**给人用的台账维护页**；
- **设备编号锁定** —— 原型里设备编号允许改（要过平台核对 + 留痕）。
  真车出厂后编号印在铭牌上、司机不该随便动，按现场管理要求把界面上的输入框
  改成只读即可，平台侧一个字都不用改；
- **字节级 HTTP Range 续传** —— 断点续传做在**批次级**（重传整个批次，
  靠幂等保证不重）。术语上不超售：这确实不是字节级续传，文档和代码里都不这么说。

另外几处工程取舍：

- **CSV 表头用 ASCII 列名**（中文名放注册表映射）—— 两个原因：
  Excel 打开不锁文件，以及避免不同区域设置下的编码问题。
  CSV 只做**不可变原始日志**，筛选 / 手动上传 / 清理全部走本地 SQLite 索引，
  就是因为 Windows 上 Excel 一打开 CSV 就会锁住文件（WinError 32）；
- **SQLite 是索引，CSV 是底账** —— 两者都有一份数据，不是冗余：
  CSV 保证"数据到手就落盘且永不修改"，SQLite 保证"能查能改状态"。
